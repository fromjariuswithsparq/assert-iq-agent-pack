# Assert.IQ / Quality Intelligence — Kiro entrypoint

This repository is governed by the Quality Intelligence (QI) operating model.
QI is the strategic frame; Assert.IQ is the accelerator.

## Operating contract — load first

The shared rulebook — core principles, maturity awareness, governance, output
standards, workspace topology, and the four-layer reasoning order — lives in
`.kiro/steering/qi-foundation.md`. It carries `inclusion: always`, so it is
already in your context. **Do not duplicate its rules here.**

That file is generated from `.github/instructions/qi-foundation.instructions.md`,
which is the single source of truth shared with Claude Code and Copilot. If you
need to change a rule, change the instruction source and re-run the Kiro sync
from the pack checkout — never edit the generated steering file. `scripts/` is
pack-only and is never installed, so that sync does not run from here.

Client-specific configuration is read from `.assert-iq/`: `config.yaml`,
`governance.md`, `maturity-profile.md`, `signal-schema.json`. Read
`maturity-profile.md` before acting — it gates which capabilities are allowed.

## Capabilities surface

- **Skills** — 31 QI skills in `.kiro/skills/`, a symlink to
  `../.github/skills` so all three harnesses run byte-identical skills.
  Invoke as `/<skill-name>` or let Kiro route by description. Highlights:
  `/risk-assess-pr`, `/release-confidence`, `/code-review`,
  `/generate-traceability-matrix`, `/generate-hotspot-map`,
  `/measure-qi-impact`.
- **Agents** — `.kiro/agents/assert-iq.md` is the lead orchestrator;
  `.kiro/agents/assert-iq-plan.md` is its read-only planning sibling. The 8
  specialists in the same directory carry `dispatchKind: sub-agent` and are
  delegated to by the lead, in parallel where independent.
- **Dreaming** — durable project memory at `.assert-iq/memory/`, consolidated
  by `/dream`. Wired through `.kiro/hooks/assert-iq-dreaming.json`
  (`SessionStart` + `Stop`).
- **Verdicts** — every `/risk-assess-pr` and `/release-confidence` result is
  recorded to `.assert-iq/verdicts/archive/` for calibration and audit.

## Kiro-specific rules

These have no Claude Code or Copilot equivalent. They are the ways this
harness will silently misbehave if you ignore them.

1. **Custom agents do not inherit steering or skills.** The default agent
   loads both automatically; a custom agent loads only what its `resources`
   field names. Every Assert.IQ agent here declares
   `file://.kiro/steering/**/*.md` and `skill://.kiro/skills/**/SKILL.md`. If
   you author a new agent, declare both — Kiro **drops invalid `resources`
   entries silently**, so a typo produces an agent with no QI rulebook and no
   error message.

2. **Never edit a generated file.** `.kiro/steering/qi-*.md` and the 8
   specialist agents are rendered by the Kiro sync. Their headers say so.
   Edits are reverted by the next sync, and check P7 in
   `.assert-iq/tests/_qi/automated/e2e-agent-parity.sh` fails while they are
   stale. The sync runs from the pack checkout — `scripts/` is pack-only and
   is never installed, so it will not resolve in this workspace. That is
   expected, not a broken install.

3. **Hooks do not run in an untrusted workspace.** If Dreaming is not
   recording sessions, check workspace trust before anything else — Kiro
   disables hook execution silently for untrusted folders.

4. **Specs are a native home for acceptance criteria.** When the user is
   working inside `.kiro/specs/<feature>/`, treat `requirements.md` as the AC
   source for traceability markers and `/generate-tests-from-ac`. Cite the
   spec path alongside the work-item ID. Do not invent a work-item ID because
   a spec exists — the rule in `qi-traceability.md` still holds: emit
   `TODO(qi-trace): unresolved` and say which value is missing.
